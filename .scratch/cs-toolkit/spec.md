# 客服工具箱 · 方向与待办

> 立项背景：用户是客服型公司，评估在现有平台（控制台 + 多实例）之上还需要补什么。
> 口径：只列「能减少员工工作量」的功能，且优先复用平台已有的四类零件。
> 本轮状态：**方向与清单已定，P0 四项已开工单等待排期**

---

## 一、判断依据

### 1. 客服的时间不在「回答」，在「查」和「搬」

真正吃掉工时的是跨系统查单、跨表搬数据、后台改单、截图取证、做报表。
所以功能要往「省掉一次切换/一次复制粘贴」上投，而不是往「帮客服组织语言」上投。

### 2. 平台已有的四类可复用零件

| 现有工具 | 沉淀下来的能力 |
| --- | --- |
| 自动化脚本助手 `rpa` | 绑窗口 + 键鼠/文本/图像/流程指令（`win`/`key`/`text`/`mouse`/`img`/`flow`） |
| 桌面图片监控 `monitor` | 屏幕区域抓屏 + OpenCV 多尺度模板匹配 + 命中记录 |
| 物流信息查询 `logi` | Excel 进出管线 + 列自动识别 + Provider 抽象（excel/web/api）+ 缓存 + 验证码检测 |
| Excel 多表对比 `cmp` | 主键对齐 + 列名智能映射 + 规则判定 + 结论分级 + 报告输出 |

**新增工具的边际成本，取决于它复用了几类零件。** 这条决定了下面的优先级。

### 3. 竞品调研结论：能力被拆开了

| 类别 | 代表 | 强在哪 | 缺什么 |
| --- | --- | --- | --- |
| RPA 类 | 影刀、UiBot、UiPath、按键精灵、AutoHotkey | 可视化编排、图像+元素双定位、断点续跑、数据表变量、组件市场 | 面向「批量跑流程」，变量与格式化是开发者视角，没有坐席手边的即时展开 |
| 坐席助手类 | 帮我吧、纷享销客、华云天下、极简云 | 实时话术推荐、客户信息弹屏、敏感行为提醒、会话摘要、一键建单 | 话术靠平台/AI 推，不让用户自定义模板去拉任意字段；绑死自家工作台 |
| 文本扩充类 | Beeftext、TextPie、TextExpander | 变量模板、光标落点、分组开关、误触发保护、托盘常驻、模糊选择器 | 变量只来自剪贴板/日期/手填，不能从窗口或表格取结构化字段 |

**组合缺口**：没有产品把「从窗口取字段 + 变量格式化 + 手边一键展开」合起来。
而平台已经具备其中 2/3（`render_template` 模板 + 窗口取字段 + 图像库）。

## 二、架构判断：先做底座，再做工具

下面五项**不是功能，是公共零件**。跳过它们直接堆工具，等于每个工具都重写一遍。

| 底座 | 解决什么 | 谁依赖它 |
| --- | --- | --- |
| 模板与格式化引擎 | 把 `{列名}` 升级成 `{列名\|格式化器}` | 登记台账、批量改单、定时提醒内容、日报、话术片段 |
| 通知通道与命中事件列表 | 「命中了怎么通知人」——现在只有记录，没有通道 | 提醒类全部、触发器 |
| 触发器 | 定时 / 间隔 / 事件三类触发 + 补跑与防重入 | 定时提醒、定时日报、定时跑批 |
| 定位器抽象 | 统一「元素优先、图片兜底」，并记录靠哪种命中 | 提醒类全部、SLA、逐步执行调试 |
| OCR | 读得出图片里的文字（现在只能匹配图形） | 一屏查单、需要「读值」的所有场景 |

**定位器为什么必须抽象**：提醒类最怕的不是不准，是**静默失配**——目标改了主题或布局，图片匹配只是永远不命中，
不报错。用户会以为在盯着，其实从第一天起就瞎了。而「数值越界 / 超时 / 状态变化」这三类提醒图片定位**根本做不到**，
只有元素定位能读出值。所以规则里两种定位器都要能填，运行时按序降级，并且**命中事件必须记录靠哪种定位命中的**。

## 三、提醒类的统一模型（定时提醒是其中一种预设）

提醒类里所有工具都是**同一条流水线**，只是触发条件和判定条件不同：

```
触发（trigger） → 判定（condition） → 内容（content 模板） → 通道（channels）
```

| 预设 | 触发 | 判定 |
| --- | --- | --- |
| 桌面图片监控（已有） | 事件 | 图片出现/消失 |
| 定时提醒（本次新增） | 定时 / 间隔 / 一次性 | 无（时间到就提醒）或 数值条件 |
| 差评哨兵 | 事件 | 文本命中关键词 |
| SLA 超时升级 | 间隔轮询 | 数值越界（剩余时长 < N）/ 状态变化 |

**所以「定时提醒」不是新工具，是提醒规则的一种预设。** 但为了用户能找到它，工具页给一个预设入口。

### 定时提醒的设计要点

| 项 | 设计 |
| --- | --- |
| 触发方式 | 一次性时间点 / 周期（每天 9:00、每周一、每月 1 号）/ 间隔（每 30 分钟）/ 高级 cron |
| 动作 | ① 只提醒人（一条通知，不需要实例）；② 启动某个实例后再提醒（跑批 + 回执） |
| 提醒内容 | 复用模板引擎：`订单号：{订单号}`、`今日未完结 {未完结数}`。**不要只给一句固定文案** |
| 通知通道 | 桌面通知 / 托盘角标 / 声音 / IM webhook / 邮件（与提醒类共用底座） |
| **补跑策略** | **必须显式定义**：电脑关机或休眠错过触发时，恢复后是「立刻补跑」还是「跳过」。这是定时任务最常见的翻车点——第二天发现昨天的日报没出 |
| 防重入 | 上一次还在跑、下次触发时间又到 → 跳过并记录，不排队 |
| 可见性 | 显示「下次触发时间」「上次执行结果」「历史执行记录」；一次都没跑成功时要显眼 |
| 与实例的关系 | 定时提醒本身不占实例；只有它的动作是「启动实例」时才牵涉实例 |

## 五、明确不做 / 缓做

1. **不做大而全的「客服中台」。** 一个工具只解决一个高频动作，员工才会用。现有「工具箱 + 每工具可多开」形态继续沿。
2. **大模型相关缓做**（AI 话术推荐、会话摘要）。理由：改造的是客服的工作习惯，阻力最大，且必须先有干净的话术库，否则垃圾进垃圾出。等 P0–P2 跑顺、拿到真实数据再上。
3. **所有「写」类自动化默认只产出「待人工确认清单」**，人在回路不可省，且必须留痕。改单、退款、改价错了是真金白银。
4. **不做「假开关」**。与 `docs/settings-flow-review.md` 同一口径：能编辑的每一项背后必须有真实字段与真实消费方。

## 六、排期前需要用户确认的三件事

1. **P0 四项是否同意开工**（尤其 02 通知通道，它是后面一半功能的前置）。
2. **定时提醒的补跑策略**：错过触发时「立刻补跑」还是「跳过」？建议默认补跑，且只补最近一次。
3. **OCR 排在哪**。它是 L 级投入，但也是竞品普遍有、平台完全空白的最大能力项。值不值得投，取决于你们有多少场景卡在「要读图上的字」。

## 七、方法论（写给后面的自己）

- **先量化再开发。** 让 2–3 个客服记一周「每半小时在做什么」，找 Top 3 重复动作。内部工具最常见的死法就是做出来没人用。
- **先做「读」，后做「写」。** 查询/汇总/告警错了只浪费时间；改单/退款错了要赔钱。
- **底座先于工具。** 底座做一次，后面每个工具都省一半工。
