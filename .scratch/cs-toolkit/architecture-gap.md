# 客服公司落地 · 技术底座差距与风险评估

> 评估对象：`auto-play-studio`（Electron + React 前端 / Python FastAPI 引擎 / 本地 SQLite）
> 视角：假设这家客服公司把这套平台铺到 **几十上百个坐席、长期跑、还要拿数据跟老板/甲方交代**，
> 从代码现状出发，回答「技术底座上还差什么、最先会断在哪」。
> 本文件**只做评估，不改代码**。所有结论都标了证据（`文件:行`），便于复核。
> 业务侧的功能缺口由产品经理并行分析，本文只讲技术底座。

---

## 〇、一句话结论

**最先会断的三个地方（按"断得最早 + 最难被发现"排序）：**

1. **「没人知道它已经瞎了」——常驻类工具没有"期望状态"、没有哑火检测、没有心跳。**
   `monitor` / `guard` 靠"轮询不报错"伪装成健康：目标窗口关了、UIA 读不到（现在 `_read_uia` 是**桩**，恒返回失败，
   实际只有剪贴板在兜底）、图片模板因 DPI/改版永不命中、引擎进程崩了 —— 全部表现为"界面显示运行中，实际零产出"。
   铺到 100 台，**没有任何手段知道哪台在真盯、哪台在空转**。这是最先断的，因为它不产生故障单，只产生"以为在监控"。
2. **「配置发不下去，也收不回来」——单点本地 SQLite，无分发、无版本、无回收。**
   现在唯一的自动化分发通道是敏感词库那一条（`wordlib.json` 文件监听，单向、无版本号、无校验、无回执）。
   实例配置、方案、知识库、话术、图片素材与阈值全部只能手工逐台配；升级后旧 `config_json` **不迁移**
   （迁移只管表结构 `PRAGMA user_version`，不管配置语义），而 `DEFAULT_CONFIG` 只对新实例生效。
   铺到 100 台就是 100 份手工配置 + 100 份对不上的版本。
3. **「本地 HTTP 引擎是全开放的单点」——无鉴权 + 固定端口 + 引擎一崩全实例停摆。**
   引擎在 `127.0.0.1:8731` 上 `allow_origins=["*"]`、无 token，任何本机进程或网页都能
   `GET /api/instances` 枚举实例、`POST /api/instances/{id}/control/start` 驱动键鼠、
   `GET /api/violations` 拿走客户聊天原文；同时它是全应用唯一的引擎进程，崩一次所有窗口的实例一起变
   `idle` 且**不会自动重启**（`recovery` 只复位、不续跑）。

## 一、能力边界评估表

> 「撑到什么规模会断」里的"规模"不只有人数，还有**时间**（常驻工具 24×7 跑几个月的衰减）。

| # | 维度 | 现状（证据） | 撑到什么规模会断 | 断的后果 | 建议补什么 |
|---|---|---|---|---|---|
| 1 | **本地存储** | 单机 SQLite（WAL），落 `userData/autoplay.db`；写入一把全局锁串行化（`db.py:334`）；`logs` 每实例上限 2000 条、**每次写日志都跑一次子查询 DELETE**（`db.py:362-370`）；`rows` / `hit_events` / `violation_events` / 命中快照 **无上限、无留存期** | 单用户够用。**断在时间**：常驻实例 24×7 跑 3~6 个月（guard 每秒一条日志 + 每次命中写一张 JPEG） | 磁盘占满、库变慢、最坏写失败中断执行；**换机即丢**（无备份机制） | 留存策略（按天/按条轮转）+ 快照目录配额 + 归档/VACUUM + 一键备份导出包 |
| 2 | **配置与资产分发** | 只有一条：`sensitive_words/watch.py` 监听 `wordlib.json`（单向、mtime+size 判变、坏文件只报一次）。实例配置 / `plans` / 知识库 / 话术 / 素材 / 阈值 **无任何分发或导入导出**（`main.py` 的 `/plans` 只有本地 CRUD） | **>5 台**就要人工逐台配；**>20 台**必然版本漂移 | 不同坐席跑不同规则与阈值，统计口径不一致；主管无法证明"所有人都在监控" | 统一分发通道（把 wordlib 那条扩成 bundle：版本号 + 校验 + 回执）+ 本机配置快照上报 |

| 4 | **可观测性与审计** | `hit_events` 能回答"命中了什么"（含 `matched_by` / `rect` / `snapshot` / 已读 / 确认）；`violation_events` 能回答"谁违规了"（`seat` / `level` / `detail` 原文 200 字）。**没有**"谁改了什么配置、谁点了开始、谁确认了告警"的操作审计；导出只有违规 CSV（前端拼，`ViolationStatsPage.tsx:87`） | 要跟老板/甲方交代时就断（第一天交付报告就撞上） | 出事（发错话术 / 改错单）无法定责复盘；合规上答不出"这条客户数据存了多久、谁能看" | `audit_log`（actor / action / target / before-after / ts）+ 统一导出（跨实例、带时间范围、可脱敏）+ 留存期与脱敏开关 |
| 5 | **稳定性与自愈** | `recovery` 启动把 live 状态复位成 `idle`（**不续跑**，`recovery.py:26`）；`engineSupervisor` 只 spawn 与置空引用，**无健康检查、无崩溃重启**；唯一有"补跑"语义的是每日汇总 pending（`daily_summary.py`） | **铺开第一天就断** | 重启/崩溃/休眠后 monitor/guard 永远停 idle，无自动拉起；休眠错过的定时任务静默丢失 | 期望状态（`desired: running`）+ 开机自启 + 引擎心跳与自动重启 + "最后一次活着是什么时候"可查询 |
| 6 | **定位与识别** | 图片模板（多尺度 TM_CCOEFF_NORMED）+ 绝对物理坐标；`matched_by` 只有 `image` / `keyword`；`text_grabber._read_uia` 是**桩**（`text_grabber.py:100-110` 恒返回 `("", False)`），guard 实际只有剪贴板兜底；无 OCR、无元素定位 | 目标系统改版 / 换机换分辨率换缩放 → 模板永不命中 | 监控"开着但瞎着"（静默）；所有"读值类"提醒（超时/越界/状态变化）**根本做不了** | 定位器抽象（元素优先 + 图片兜底 + 记 `matched_by`）+ 哑火检测；OCR 视场景定 |
| 7 | **安全与合规** | 词库/话术/知识库/素材明文落 `userData`；`violation_events.detail` 存客户原文 200 字，**无脱敏、无留存期、无加密**；本地 API 无鉴权 + CORS `*`；写类自动化无二次确认（README「下一步」里仍挂着未做） | 第一次有甲方/监管来问，或第一次误发 | 合规风险 + 真金白银的错操作 | 本地 API 加 token（preload 注入）+ 原文脱敏与留存期 + 写类二次确认与留痕（与 spec 五.3 同口径） |
| 8 | **部署与运维** | electron-builder（nsis + portable，**无签名、无 auto-update、无 publish**，`package.json:69-114`）；PyInstaller sidecar 依赖 `--paths notic --collect-submodules app`（顶层包名 `app` 极易撞车）；**`requirements.txt` 里 pyautogui / opencv / pillow / pywin32 / comtypes 全是注释掉的**，但 `monitor.py:19` 与 `snapshots.py:19` 在**模块顶层** `import cv2` | **要发第二版时就断** | 100 台手工升级/回滚；构建机环境漂移 → 打出的包缺 cv2，monitor 在运行期才炸（且以"实例 error"呈现，看不出是打包问题）；未签名 → SmartScreen 拦截 / IT 禁用 | 依赖收敛（顶层 import 的库必须写进 requirements，CI 加一条"import ↔ requirements 对齐"检查）+ 版本号与更新通道 + 一键排障包（db 摘要 + 日志 + 版本 + 环境信息） |
| 9 | **性能（最致命）** | 每个 monitor 实例**各自** mss 全屏抓帧 + cv2 匹配，默认 500ms 一轮，**无帧共享、无全局节流**（`monitor.py:237-264, 307`）；guard 默认 800ms 轮询；声音告警走 PowerShell TTS，**每次命中起一个子进程**（`notic/app/core/sound.py`）；Electron 主进程 2s 轮询 outbox | 低配机 + 开 2~3 个常驻实例就断 | CPU/内存常驻占用推高，客服聊天工具变卡 → **客服会主动关掉它**。这是唯一能让项目直接归零的失败模式 | 抓屏帧共享 + 自适应轮询（无变化降频）+ 声音预生成/复用进程 + "低配模式"总开关 + 资源占用自报可见 |

## 二、必须先做的底座

> 量级沿用 spec 的相对刻度 S < M < L。

|---|---|---|---|---|---|

| **S-03** | **触发器底座** | 用户点名的定时提醒直接依赖；补跑策略必须在这一层定死 | **M** | S-02 | 与 spec 一致。注意：**补跑语义要覆盖"机器关机/休眠"**，不能只覆盖"发送失败"（现状只有后者） |
| **S-05** | **定时提醒**（S-03 的预设） | — | **M** | S-02 / S-03 | 与 spec 一致 |

### 与 spec 的冲突与调整（明确标注）

**① S-06 定位器抽象：spec 标 P1「依赖 —」，建议提到 P0。**
- **理由**：spec 二.自己的论证（"最怕的不是不准，是静默失配"）已经把它定性为**正确性**问题而不是能力扩展问题。
  而 S-11（差评哨兵）、S-12（SLA 超时）、S-17（一屏查单）全部压在它上面，串行排在 P1 会让整条链推迟两轮。
- **不改** spec 的"元素优先 + 图片兜底 + 命中必须记 `matched_by`"设计，只调优先级。

**② S-08 建议从 P1 提到 P0，并把 S-02 状态从 `in-progress` 更新为"接近完成"。**
- **理由（基于代码，不是基于排期）**：`notify/` 下 desktop / webhook / 静音时段 / outbox / wording 已全，
  `hit_events` 已带已读与确认闭环，每日汇总已有 pending 补发。
  也就是说**"命中了怎么通知人"这条已通**；剩下真正卡住生产可用性的是"它到底有没有在盯"（A-01 / S-08）。
  继续按 P1 排队，等于把"监控类工具在生产里有没有用"的验收放到很后面。
- 与 spec 不冲突之处：spec 二.已经把"哑火"列为定位器必须抽象的核心理由，本条只是把它提前。

**③ S-10 OCR：不改优先级（仍 P2），但建议前面插一个 S 级"能力探测"。**
- **理由**：OCR 不是一个纯功能项，它会改变**打包体积与低配机内存**（几百 MB 级 vs 现在的几十 MB），
  直接顶到"客服会关掉它"这条红线。在决定投入 L 之前，应先花 S 验证两件事：
  （a）真有多少场景卡在"要读图上的字"；（b）Windows 自带 WinRT OCR（**零打包体积**）够不够用。
- 建议形态：先接 WinRT OCR（Win10+ 自带、无新依赖），不够再引 RapidOCR（onnxruntime，仓库已在用，见 `kb/embed.py`）。

**④ spec 五.3「写类自动化必须留痕」目前无落点，建议新增为一个底座项（即 A-04 的一部分）。**
- **理由**：这条是每个"写"类工具都要遵守的约束，若不在底座层做成机制（二次确认 + 留痕），
  就会变成每个工具各写一遍，且迟早有工具漏掉 —— 而漏掉的代价是真金白银。

## 三、风险清单

> 【静默】= **不报错但结果错**。这类最危险：它们不产生故障单，只产生"以为在工作"。

| # | 风险 | 触发条件 | 是否静默 | 后果 | 先补什么 |
|---|---|---|---|---|---|
| R1 | **UIA 读取是桩**：`_read_uia` 恒返回 `("", False)`（`text_grabber.py:100-110`），guard 永远降级到剪贴板 | 任何一次 guard 运行 | **【静默】** | 界面写的是"盯住聊天输入框"，实际只监控剪贴板；**客服直接打字不复制 → 完全监控不到**，而词库/统计看起来一切正常 | S-06（真 UIA 实现）+ A-01（哑火检测） |
| R2 | **模板哑火**：分辨率 / 缩放 / 主题 / 目标改版 → 图片永不命中 | 换机、改 DPI、目标系统更新 | **【静默】** | 监控"运行中"但零产出；主管以为有人在盯 | A-01 + S-06 |
| R3 | **引擎进程死了没人知道**：`ensureRunning` 无周期健康检查，只在启动时调用一次 | 引擎崩溃 / 端口被占 | **【静默】** | 界面操作无响应或数据停在旧值，用户只觉得"卡了" | A-01（心跳）+ A-05（端口收敛） |
| R4 | **崩溃恢复只复位不续跑**：`RECOVERED_STATUS = idle`，monitor/guard 停在 idle 等人点开始 | 引擎重启 / 崩溃 / 系统重启 | **【静默】** | 无人值守期间**零监控**，且没有任何提示 | A-01（期望状态 + 开机自启） |

## 四、给用户的三件事（需要你现在拍板的技术取舍）

### 决策 1：本地优先，还是要一个（哪怕是内网一台机器的）服务端？

**为什么现在要定**：A-03（分发）、A-01（心跳）、A-04（审计导出）这三件事的形状完全取决于这个答案。

| 选项 | 能得到什么 | 要付出什么 |
|---|---|---|
| **A. 纯本地优先**（数据不出本机） | 零运维、零合规负担、离线可用，符合现有 ADR-0001 的取向 | 分发只能走共享盘文件；**"发没发到"不可知**；汇总数据只能人工逐台导出再拼 —— 跟老板交代时要人肉收 100 份 CSV |
| **B. 本地优先 + 单向可上报**（推荐） | 配置下发走共享盘/内网 HTTP；运行数据**可选**上报到内网一台机器做汇总看板；个体客户数据仍留本机 | 多一台内网机器的运维；上报内容必须先定义清楚（默认只报聚合数与心跳，不报原文） |
| **C. 上完整服务端** | 集中配置、集中审计、实时看板 | 客户数据出本机 → 合规责任陡增；需要后端团队与运维，与"桌面工具"定位冲突 |

**建议 B**。它的关键点是：**先把"上报什么"定义死**（默认只报心跳、版本号、聚合计数），
这样即使将来甲方来问，也能回答"原始客户数据从未离开坐席本机"。

### 决策 2：要不要引入 OCR 依赖？（这不只是功能选择，是打包体积与性能的取舍）

| 方案 | 打包体积/内存影响 | 中文效果 | 适用判断 |
|---|---|---|---|
| **Windows 自带 WinRT OCR**（`Windows.Media.Ocr`） | **几乎为零**（系统自带，无新依赖） | 一般，对截图小字号/复杂背景较弱 | 先拿它做 S 级能力探测，验证"要读图上的字"的场景到底有多少 |
| **RapidOCR（onnxruntime）** | 中等（约十几 MB 模型 + onnxruntime，后者仓库已在用） | 较好 | 若 WinRT 不够，这是性价比最高的一条 |
| **PaddleOCR** | **重**（几百 MB 级依赖树，打包体积与内存都顶到红线） | 最好 | 除非有明确的高难度场景，否则不建议 —— 它会直接顶到"客服会关掉它"那条生死线 |

**建议**：先做 S 级探测（WinRT OCR + 3~5 个真实场景），拿到结论再决定要不要投 spec 里的 L 级 S-10。
**在这条定下来之前，不建议在打包里塞任何 OCR 依赖。**

### 决策 3：配置分发通道用哪种形态？

| 选项 | 优点 | 缺点 | 能不能回答"发到了吗" |
|---|---|---|---|
| **共享盘文件**（现有 wordlib 思路） | 零新增组件、零运维、离线可用 | 无法确认谁收到了；无版本、无灰度、无回滚 | **不能**（除非每台写一个回执文件） |
| **内网 HTTP** | 能收回执、能做版本与灰度、能回答覆盖率 | 要一台机器 + 一个最简服务 | 能 |

**建议：先走共享盘，但必须带版本号 + 回执文件**（每台应用成功后往共享盘写一个
`last_applied.json`，含机器名 / 版本号 / 时间）。
**没有回执的分发，在合规场景里等于没发** —— 出事时你无法证明"当时所有坐席用的都是 v3 词库"。
这一步是 S 级，但它是 A-03 能不能真正落地的前提。
