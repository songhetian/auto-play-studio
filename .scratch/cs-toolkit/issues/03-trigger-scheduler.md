# 03 · 触发器底座（定时 / 间隔 / 事件）

Status: needs-triage
Priority: P0
Type: task
Blocked by: 02

## 背景

用户明确点了「定时提醒」这个功能。但定时提醒是这个底座的一种预设用法，
**先做底座，后面定时日报、SLA 轮询、定时跑批都直接复用**，不必各写一套调度。

依赖 02：触发器触发之后总得有个出口，通知通道是它的前置。

## 目标

### 三类触发

| 类型 | 表达式 |
| --- | --- |
| 定时 | 每天 9:00 / 每周一 / 每月 1 号；高级可填 cron |
| 间隔 | 每 30 分钟 / 每 2 小时 |
| 事件 | 由命中事件驱动（依赖 02 的事件模型） |

配套还有**一次性时间点**（「明天下午 3 点提醒我」）。

### 触发后的动作

1. **只提醒人** —— 不需要实例，直接产出一次通知
2. **启动某个实例** —— 跑批，结束后回执结果

### 必须处理好的四个硬问题

| 问题 | 要求 |
| --- | --- |
| **补跑策略** | 电脑关机/休眠错过触发时，「立刻补跑」还是「跳过」必须**显式可配**，并默认补跑且只补最近一次。这是定时任务最常见的翻车点——第二天发现昨天的日报没出 |
| **防重入** | 上一次还在跑、下次触发又到 → 跳过并记录，不排队 |
| **休眠检测** | 用 Electron `powerMonitor` 的 resume 事件判断「刚被唤醒」，据此决定补跑 |
| **时区** | 统一按本机时区，界面上明确写出「每天 09:00（本地时间）」 |

## 验收标准

- [ ] 能配出「每天 09:00 启动某实例」并真的按时跑
- [ ] 完全关机跨过触发点后重新开机，按策略补跑且**只补一次**
- [ ] 上一次未结束时到点，跳过并留下「已跳过」记录
- [ ] 页面上能看到：下次触发时间、上次执行结果、历史执行记录
- [ ] 「从来没跑成功过」的任务要显眼（红标 + 原因）
- [ ] 调度的纯计算部分（下次触发时间、是否需要补跑）有单元测试，不依赖真实时钟

## 涉及文件

- `python/engine/`（新增调度模块；纯计算函数与 IO 分离，便于测试）
- `electron/main.ts`（`powerMonitor`）
- 新增触发器管理页面
