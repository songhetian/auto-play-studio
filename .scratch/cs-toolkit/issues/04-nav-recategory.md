# 04 · 导航重分类：提醒类 / 辅助操作类

Status: done
Priority: P0
Type: task
Blocked by: —

## 背景

现在的分组是「按产物格式」分的，不是「按工作模式」分的，结果把工具挂错了组：

`src/app/navModel.ts` 现在长这样：

```
工作台 / 执行类工具（rpa, monitor）/ 数据类工具（logi, cmp）/ 资源 / 系统
```

**`monitor` 挂在「执行类工具」下是错的。** 它不是批处理执行器，是常驻盯屏的提醒器 ——
`instanceStatusSchema` 里那个 `armed` 状态就是为它准备的，说明当初设计时也是这么想的，只是分组没跟上。

## 目标

分类标准改成「**谁触发、产出什么**」：

| 分组 | 触发 | 产出 | 成员 |
| --- | --- | --- | --- |
| 执行类 | 程序调度 | Excel / 状态回写 | `rpa` |
| 数据类 | 程序调度（不碰屏幕） | Excel / 报告 | `logi`、`cmp` |
| **提醒类**（新） | 外部事件 | 通知 + 待办 | `monitor` |
| **辅助操作类**（新） | 人（快捷键） | 当前窗口里的结果 | 暂无 |

执行类与数据类的区别是「动不动屏幕」，两者都属无人值守，**保留现状**，只把 `monitor` 挪出去。

## 注意事项

- **不要显示空的「辅助操作类」分组**。等它有了第一个工具（话术片段库）再出现在导航里，
  否则用户点进去看到空列表会以为坏了。分组定义可以先写好、先不渲染。
- 导航的搜索、面包屑、选中态都从 `navModel.ts` 派生，改完要跑 `navModel.test.ts` 确认它们自动跟随。
- 控制台总览页的「工具箱」分段卡片网格与导航分组是同一套语义，要一起改，**不能导航分好了但总览页还按老分类**。

## 立项后的两处修正（原文写于 macro 之前）

### 1. `macro` 也归「辅助操作类」

原文的分组表里「辅助操作类」写的是「暂无」—— 那时 `macro`（工单 19）还不存在。
按本工单自己的定义（**触发 = 人按快捷键，产出 = 当前窗口里的结果**），`macro` 完全符合：
它就是「按一下 F8，在当前窗口里走一串按键」。用户已裁定归入辅助操作类。

于是「执行类」里只剩 `rpa`：它才是那个「程序调度、按 Excel 逐行跑、回写状态」的工具。
这么归完，分组才真的在回答「谁触发、产出什么」，而不是「产物是什么格式」。

### 2. 总览页与导航是**两套来源**，这才是「不一致」的根因

`DashboardPage.tsx` 里写的是：

```ts
const execTools = TOOLS.filter((t) => t.id === 'rpa' || t.id === 'monitor')
const dataTools = TOOLS.filter((t) => t.id === 'logi' || t.id === 'cmp')
```

分组改在 `navModel.ts`、分段却硬编码在页面里 —— 改一边另一边不会变。
同页的「资源与系统」入口**已经**是派生写法（`NAV_GROUPS.filter(...)`，工单 20 修的），
工具分段是漏掉的那一半。所以本工单的验收标准「总览页分段与导航分组一致」不是靠肉眼比对，
而是要把「分段」也变成一个派生函数，让不一致**不可能发生**。

### 3. 工具元数据有两份，且已经漂了

`label / desc / icon / color` 在 `moduleRegistry.TOOLS` 与 `navModel.NAV_GROUPS` 各存一份。
`rpa` 的说明在两处已经不一样：

- 注册表：`绑定一个目标窗口，按 Excel 数据逐行执行脚本指令`
- 导航：`绑定窗口，按 Excel 数据逐行执行脚本指令`

同一个工具，侧栏显示一句、工具卡显示另一句。漂移不需要谁来改错，**只要有两份就会漂**。

用户裁定：**一并收敛**。分工定为 ——

- `moduleRegistry.TOOLS` = 工具**是什么**（名字/说明/图标/颜色/搜索别名/**归哪一组**）
- `navModel` = 它在**信息架构里的位置**（分组的顺序、标题、一句话 hint；非工具条目如总览/实例管理/资源三页仍在这里声明）

## Comments

- 2026-10-02 完成（前端 450 / typecheck 干净 / 截图 14 镜头）。值得留下的几条：
  - **对账器反证过**：故意把 `macro` 的 `group` 拼成 `'assit'`（工具静默从导航消失）、
    故意让两个分组同 id（同一工具出场两次），`每个已登记的工具都出现在导航里，且恰好一次`
    两次都红。这个测试不是空转的。
  - **「每个工具恰好一次」的测试不是套套逻辑**：它不是把派生代码再算一遍，而是拿
    `TOOLS`（注册表）与 `NAV_GROUPS`（渲染出的信息架构）两个**独立清单**对账，
    真正的失效方式是 `group` 拼错导致工具静默消失 —— 这正是它要拦的。
  - **截图的 `inViewport` 会被侧栏同名文字骗到**：总览页要验「辅助操作类分段看得见」，
    滚到「辅助操作类」四个字 —— 侧栏分组标题也是这四个字，永远在视口里，断言于是假通过。
    改成滚到**只有总览页才有**的那句 hint。同 21 的「等待条件别用页头文案」，同一个病：锚点要唯一。
  - **验收脚本必须不依赖产品端口**：8731 上常驻着打包应用的 `autoplay-engine.exe`
    （用户开着窗口它就在跑）。nav 第一轮就是在 8731 上起引擎，uvicorn 绑不上（winerror 10048）
    **静默退出**，curl 和 Electron 照样连上那个别人的引擎 —— 断言全过、打印 all done，
    验的却是**完全不同的数据**（还把两个测试实例写进了打包应用的库里，见下）。
    修法：验收固定自己的端口（8799）+ 渲染进程里 `webRequest` 把 8731 的请求重定向过去 +
    「实例总数必须是本次造的 2」这条**独立真相源**断言。产品代码一行没动。
  - **侧栏与总览页是两套来源**这件事，靠「改成同一处派生」修掉，而不是靠肉眼比对 ——
    不一致应该在结构上不可能发生，而不是每次改完都人肉对一遍。
