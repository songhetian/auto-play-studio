## 一、一句话结论

**spec 已经把「单坐席效率」这一层铺满了（省一次切换、省一次复制粘贴），但它通篇的主语是「实例」和「本机」，不是「人」和「团队」。**
一家客服公司真正的空白在另外两层：

1. **落地验证层** —— 没有任何一项能回答「做出来的东西有没有人在用」。spec 方法论第一条自己写了「内部工具最常见的死法就是做出来没人用」，但 18 项待办里没有一项能量化这件事。这一层是空的，后面所有投入的优先级都排不准。
2. **沉淀闭环层** —— 知识库能搜、话术库能插，但**客服搜不到的时候补不了一条**。库是只读的静态库，用完一次就退化一次，永远长不大。
3. **管理闭环层** —— 违规有记录、跑批有日志，但**全部归「本机」不归「人」**（`seat` 字段只写在 `violation_events` 一张表里，取值还是 `os.getlogin()`）。质检、考核、交接、申诉全部没有主语，做不动。

所以最该补的三件：**①用量与活跃度统计 ②知识与话术「搜不到→补一条」闭环 ③值班人标识与换班交接**。
这三件都是 S/M 级，且都不依赖 spec 里还没做的 OCR（#10）与定位器（#06）——**现在就能开工，不用排队**。

> **v2 修订（与架构评估对齐后追加）**：还有一个前提必须写在结论里——**「质检/考核」这一层暂时做不了，因为它的输入数据不可信**。
> 敏感词监控的 UIA 读取目前是桩（已复核 `python/engine/text_grabber.py:100-110` 恒返回 `("", False)`），实际只有剪贴板兜底，
> **客服直接打字完全监控不到**。也就是说「违规统计页」和「每日汇总播报」现在给主管看的是一个**系统性偏少且覆盖率未知**的数。
> 拿它做考核，考核就是错的（详见第六节 A）。因此：**定位器 #06 是质检与考核数据可信度的根，应立刻启动，与上面三件并行**。

## 二、现有能力地图（已有 / 覆盖到哪一步 / 断在哪）

| 已有能力 | 覆盖到哪一步 | **断在哪**（本轮要盯的就是这一列） |
| --- | --- | --- |
| 键鼠驱动 `rpa`/`macro` | 绑窗口 → 按 Excel 逐行执行键鼠/文本/图像/流程指令；已有屏幕互斥与组合键语汇 | **只能「做」不能「读值」**：没有 OCR、没有元素定位，读不出屏幕上的数字与状态；且中文输入走剪贴板（`pyautogui_driver.py:57-59`），与 guard 读剪贴板撞车（架构 R15） |

| Excel 管线 `logi`/`cmp`/`excel_prep`/`excel_toolbox` | 上传 → 列识别 → 体检/整理/合并/去重/对比 → 出新文件 + 改动台账 | **处理完就结束了**：结果不进任何台账，跑过什么、改过什么无法回溯（spec #07 未做） |
| 模板引擎 `template.py` | `{列名\|格式化器}` 渲染，八片全绿 | 只用在话术与提醒文案；**没用在报表、交接内容、审计导出**这类「给主管看」的产出上 |
| 全文 + 语义检索 `kb/` | 登记文件夹 → 索引 → 正文/拼音/语义检索；坐席面板 `Ctrl+Alt+K` 速填 | **来源是磁盘文件**，客服当场补不了一条；**零结果完全没记录**，不知道库里缺什么 |
| 通知与命中事件 `notify/` | 桌面/托盘/声音/IM webhook/邮件五通道 + 独立 `hit_events` + 静音时段 | 只服务「机器命中」；**没有「人对人」的通知**（交接、申诉、待审、待办） |
| 敏感词与违规统计 `guard`/`sensitive_words` | 命中落库 → 按词/危级/时间聚合 → 导出 CSV → 每日 IM 播报 | **只有「有没有踩雷」，没有「服务好不好」**；没有申诉与误报回流；`seat` = 本机用户名，多人一机时归错人。**更严重的是 `_read_uia` 是桩**（架构 R1，已复核 `text_grabber.py:100-110` 恒返回 `("", False)`）→ 实际只有剪贴板兜底，**客服直接打字完全监控不到，违规数系统性偏少**，而统计页与日播报都把它当全量在用 |
| 话术库 `phrases` | 模板 + `{占位符}` + 速查面板 + 一键填入输入框（不发送） | **标题唯一、覆盖即更新**：无版本、无审批、无「这条有没有用」的反馈；改错了回不去 |
| 运行记录 `instances`/`runs`/`rows`/`logs` | 每次跑批有行级结果与日志 | **没有「谁跑的」**（`runs`/`logs` 里没有 seat）；没有跨次汇总；没有对外导出 |
| 方案库 `plans` | 全局配置模板，跨工具跨实例复用，新建实例可套用 | **只在本机**：10 个坐席要配 10 遍，没有导入导出/分发 |
| 流程分步引导 `flow/` | 流程 + 步骤 + 界面图 + 圈注要点 | **只是一份文档**：无完成记录、无打卡、无考核，走没走过、会不会没人知道 |
| 坐席悬浮球 `attendant/` | 四态状态机（常态/告警/待处理/离线）+ 速查面板 + 物流 CSV 查询 | **待处理只挂在本机窗口上**，换班就没了；不认得「当前正在服务的客户是谁」 |
| 日汇总播报 `daily_summary.py` | 当天违禁词命中汇总推 IM，断网 pending 补发 | 只播违规一个数；**不是「今天整体干得怎么样」的经营日报** |
| 快照与取证 `snapshots.py` | 命中瞬间截图落盘（存路径不存 base64） | 有产生、无治理：**没有留存期、没有清理、没有归档导出**（spec #15 未做） |

### 不做（并说明理由）

| 项 | 不做的理由 |
| --- | --- |
| **多渠道统一归集**（电话/在线/工单/邮件） | 等于做客服中台，spec 第五节已明确否决；京麦/千牛/企微自身已承担归集，重复建设。只做到「会话留痕（G04）」这一层为止，不做工单流转 |
| **话务量预测** | 需要足量历史数据 + 模型，投入 L 级；且未确认存在「排不开人」的实际痛点。真有需求先看 G10 + G05 的原始趋势就够用 |
| **绩效薪酬计算** | 越界——考核标准是管理问题不是工具问题。本轮只做到「数据可导出（G05/G08）」，公式留给 Excel |
| **AI 会话摘要 / AI 质检** | spec 第五节已裁定缓做；且它依赖 G04 会话留痕与干净的话术库，**顺序不能反**。G04 做完后这条才能重新评估 |
| **账号体系 / 服务端多机同步** | 现在架构是单机本地优先（zustand persist + SQLite），做服务端等于换架构。多机分发用 **G11 方案包**替代，成本差一个数量级 |
| **工单转派系统** | 同上，属中台范畴。轻量替代：G06 交接板 + 待办认领，不做状态机 |

## 四、建议的下一步 3 个动作（可直接开工）

### 动作 1：给所有事件装上「人」——值班人标识与 seat 归位（G02，S）

具体做法：

1. `db.py` 加一张 `operator`（`id / name / code / active / created_at`）与一张 `duty_log`（`seat / operator_id / since / until`），以及一个 settings 项 `currentOperator`。
2. 先做**手选不做登录**：设置页加一个「当前值班人」下拉（数据来自 `operator`），切换时写一条 `duty_log`。理由：登录改造面大，且多人一机的场景下「切一下」比「登一下」更真实。
3. 把 `seat` 的取值从 `os.getlogin()` 改成 `currentOperator`，并把 seat 列从 `violation_events` **铺到 `runs` 与 `usage_events`**（现在 `runs`/`logs` 里根本没有 seat，这是 G05 员工维度报表做不动的根因）。
4. 产出验收：违规统计页多出一个「按人」筛选轴，且能筛出「上白班的小张」。

### 动作 2：装上「有没有人在用」的眼睛——用量埋点与活跃度页（G01，S）

具体做法：

1. `db.py` 加 `usage_events(ts, seat, kind, tool, target, ok)`，`kind` 枚举：`instance_start` / `run_finish` / `hit` / `phrase_insert` / `kb_search` / `excel_op`。
2. 五个埋点位置：实例启停（`main.py`）、跑批完成（`runner.py`）、命中上报（`monitor.py`/`sensitive.py`）、话术插入（前端 `assist` 填入成功后回写）、KB 搜索（`kb/routes.py`）。**写入失败一律静默，绝不能影响主链路**（与 `snapshots.py` 同一口径）。
3. 新增 `/usage` 页（归「系统」组），三块内容：按 人×工具×天 的热力表、**「配了但 7 天没跑过」的僵尸实例清单**、每个工具的周活跃人数趋势。
4. 产出验收：装完两周后能回答「6 个工具里哪几个是真在用的」。

### 动作 3：让知识库自己长大——零结果漏斗 + 坐席补录（G03，M）

具体做法：

1. `db.py` 加 `kb_gap_queries(query, seat, ts, resolved)`：`kb` 搜索返回 0 条时写一行。这是「库里缺什么」的唯一真实来源，现在完全没有。
2. 加 `kb_note`（不落文件的轻量知识条目：`title / body / author / status(pending|approved) / created_at`），**走同一套 `kb/` 索引器**，让手工补的条目和文件里的文档一起被搜到。
3. 坐席速查面板（`attendant`）搜不到时，把「没有结果」变成一个动作按钮「补一条」——填完进待审。
4. 资源组加一页「待补知识」：零结果查询 TOP 20 + 待审条目列表；主管点「合入」才进正式知识库，并走通知通道提醒提单人。
5. 产出验收：一个月后「零结果率」下降，且待补清单收敛为新问题而不是重复老问题。

> 顺序建议：**动作 1 → 动作 2 → 动作 3**。动作 1 是动作 2、G05、G06、G08 的共同前置；动作 2 最轻且立刻能验证 spec 方法论第一条；动作 3 是唯一能让知识库不再退化的投入。
> 三个动作都不碰 spec 的 P0/P1 在办项（#02 通知、#03 触发器），可并行不抢人。

## 五、必须向用户确认的问题（5 条）

1. **团队规模与机器形态**：现在几个坐席？是每人一台机器，还是多人共用一台？共用时怎么区分是谁在操作（有没有工号/域账号，还是纯靠人自觉）？
   → 决定 G02 做「手选值班人」还是必须做登录；也决定 G05 员工维度报表的粒度。

2. **客服实际在用哪几套系统**：京麦 / 千牛 / 企微 / 自有工单？这些系统有没有开放 API 或导出功能？
   → 决定 G04 会话留痕是「抓屏读文本」还是「接数据」；也决定 G16 客户档案到底做不做得出（拿不到客户标识就做不了）。

3. **现在有没有质检标准**：谁在抽检、多久抽一次、抽多少条、抽完记在哪（Excel？纸质？没记？）？有没有现成的评分卡？
   → 决定 G15 是「照搬现有表格」还是得先帮他定标准——后者工作量翻倍且容易做成没人用的形式主义。

4. **老板或甲方现在要你们交什么数据**：交什么、多久一次、什么格式？**甲方或合规有没有规定数据留存期**（聊天原文、截图各留多久）？
   → 决定 G08 审计导出与 G20 月报的字段，以及 G09 留存期的默认值（我的建议起点：违规原文 90 天、命中快照 30 天、运行日志 60 天）。不先对齐，做完一定对不上，这是最容易白做的一项。

5. **能不能给两段真实样本**：① 一天的客服聊天记录片段（可脱敏）② 一份你们现在手工做的日/周报表？
   → 决定 G04 / G05 / G20 的字段设计和量级估得准不准。spec 方法论第一节就写了「先量化再开发」，但量化需要样本，现在手上没有。

### A. 一条改变结论的发现：违规数据现在不可信，质检/考核层必须等 #06

我复核了 `python/engine/text_grabber.py:100-110`：`_read_uia` 只 import 了 `comtypes`，随后**无条件 `return "", False`**，真正的读取从未实现。
`_read_once` 因此永远走到 `pick_capture_mode(supports_uia=False, ...)`，实际通路只有剪贴板一条。

架构把它记为 R1（技术风险）。**从业务侧看它的后果还要再重一层**，因为它是我整列「管理闭环」的输入：

| 后果 | 说明 |
| --- | --- |
| **① 违规数系统性偏少，且覆盖率未知** | 客服直接打字（不复制）→ 完全监控不到。「违规统计页」与「每日汇总播报」现在把剪贴板能看到的当全量在用。主管每天早上看一个偏少的数，会形成**稳定的错误认知** |
| **② 更糟的是掺假数据**（架构 R15） | `rpa` 中文输入走 pyperclip **写**剪贴板，`guard` **读**剪贴板且不区分来源 → **机器人话术被当成客服说的话，记进违规台账**。漏数据是偏低，掺数据是**冤枉具体的人**；配上 G02 值班人标识后，就变成「这笔假违规记在了小张头上」 |
| **③ 因此质检/考核/申诉全部后置** | 在 #06 落地前，任何以违规数为输入的考核、评分、申诉机制上线都是错的——员工一旦发现数据不准，会连带否定整个系统 |

**我的立场：支持架构把 S-06 提到 P0，并补一条他没写的业务理由。**
spec 提 S-06 的理由是「提醒类静默失配」（机器在盯但没看见），这当然成立；
但对一家客服公司，S-06 更大的意义是**它是质检与考核数据可信度的根**。这条理由对老板更有说服力，建议一并写进工单。

**据此修订清单：**

- **G04 会话流水自动归集**：P1 → **P2（阻塞）**，依赖 spec #06。现状做不出全量流水。
- **G05 员工维度报表**：保留 P1，但**违规维度额外依赖 #06**（产能维度来自 `runs`，不受影响，可以先上产能部分）。
- **G15 拆成两条**（这是我基于阻塞做的重新分解，不是简单降级）：
  - **G15a「抽检抽样器 + 评分卡 + 汇总」（M，P1，不依赖 #06）** —— 想清楚了：抽检本来就该是「系统决定抽谁 + 系统记分数 + 系统汇总」，
    **会话内容由质检员自己看**，不需要系统能读屏。这样 L 级变 M 级，且立刻可做。
  - **G15b** = G04，等 #06。
- **G16 客户小档案**：随之在 #06 之后评估。
- **过渡期建议**：在 #06 落地前，每日汇总播报要么**加一行「当前仅覆盖剪贴板可见内容」的免责说明**，要么暂停。否则错误认知每天都在加固。

### C. 我补充的业务侧判断（架构未展开，但影响他的优先级）

1. **补跑只覆盖「发送失败」不覆盖「未触发」（架构 R5）**，业务后果比技术描述更常见：G06 交接板、G20 月报、spec #13 日报都走定时，

   所以「先保证它不卡」是「先量化它有没有人用」的前提。
