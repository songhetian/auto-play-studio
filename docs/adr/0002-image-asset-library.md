# 2. 图像素材独立成库，指令只存 assetId

日期：2026-01-02
状态：已采纳

## 背景

RPA 的图像指令（「等图出现后点击」）需要一张模板图。最直接的实现是把图片字节内嵌进实例配置里（base64），配置和图片一起走 JSON。

问题是：

- 同一张「确定」按钮的图，三个实例各存一份字节，改一次要改三处；
- 删素材没有任何拦截手段 —— 删掉之后那些指令下次执行会莫名其妙失败，而且很难查；
- 每次读写实例配置都要搬运几百 KB 的 base64，日志和导出都变臃肿。

## 决策

**图片存素材库，指令里只留一个 `assetId`。**

- 磁盘：`AUTOPLAY_ASSETS_DIR` 下按 `id` 命名（默认是库文件旁边的 `image_assets/`）；
- 数据库：`image_assets` 表存展示名、尺寸、阈值、标签；`id` 是 `img_` + 10 位随机。

由此推出三条配套规则：

1. **展示名与文件名解耦。** 文件名用 id 而非原名 —— 中文名、重名、`../` 路径穿越这三类问题一次性规避，重命名也不用动文件。
2. **删除默认拦被引用的。** `image_refs.find_references()` 扫全部实例的指令，找到「哪个实例的第几条指令」；被引用时删除返回 409 + 引用清单，只有显式 `force` 才真删，并把那些指令的 `assetId` 清空。清引用只写在 `image_library.delete_image` 这一条路径里 —— 两条删除路径各有一套 `force` 语义，是留下悬空引用的直接原因。
3. **引用体检。** `audit()` 报出「引用了不存在的素材」和「素材文件丢了」。配好之后就能查出来，不用等执行到那一条才报错。

## 后果

好处：

- 一张图改动，所有引用它的指令一起生效；
- 删素材有据可依，能回答「谁在用」；
- 实例配置保持小体积，可直接导出分享。

代价与边界：

- 素材库必须与实例配置一起迁移/备份，单独拿走 `instances` 表会全是悬空引用 —— 体检能查出来，但不会自动修；
- `audit()` 是整库扫描，实例数量很大时是 O(实例 × 指令)，当前规模（几十个实例）无压力；真到上千再考虑加索引或反向引用表；
- 素材文件名不含原扩展名信息，格式靠文件头判断（`image_meta.sniff`），所以改扩展名不影响识别。

## 备选方案

- **配置内嵌 base64**：见上述问题，未采纳。
- **只存路径，不建库**：无法回答「谁在用」，删文件与删记录会各说各话；也无法存阈值、标签这些元数据。未采纳。
- **反向引用表（asset → 指令）**：写配置时同步维护，查引用 O(1)。代价是每次改配置都要维护一致性，目前扫一遍够快，先用扫描，真成瓶颈再加。
